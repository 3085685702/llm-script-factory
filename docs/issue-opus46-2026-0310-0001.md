## 一、安全类问题

### 1.1 🔴 Settings API 无任何认证保护
- **位置**：`backend/api/routers/settings.py`，全部端点
- **问题**：API Key 的 CRUD 端点（`PUT /api/settings/keys/{key_name}`、`DELETE`、`POST /keys/validate`）与模型配置的 CRUD 端点均无认证。虽然 CORS 限制了 `localhost:3000`，但任何本地进程或浏览器扩展均可直接调用 `127.0.0.1:8000` 的敏感接口，读取 / 修改 / 删除 API Key。
- **建议**：增加最低限度的认证机制（如本地 Token 或 Secret Header），或至少对写操作做二次确认。

### 1.2 🔴 API Key 明文写入 `.env` 并同步至 `os.environ`
- **位置**：`backend/services/api_key_service.py::_write_env` (L52-53)
- **问题**：`set_key` 不仅将 Key 明文写入 `.env`，还通过 `os.environ[key] = value` 热加载到进程环境变量。若后端暴露了 `/debug` 等端点或日志泄露，Key 可被读取。
- **建议**：避免在运行时直接设置 `os.environ`，改用配置重载机制；或至少在 `validate_key` 接口中不要接受完整 Key 值作为请求体。

### 1.3 🟡 CORS `allow_methods=["*"]` / `allow_headers=["*"]` 过于宽泛
- **位置**：`backend/main.py` (L33-34)
- **问题**：在本地工具场景下风险较低，但若未来部署到公网或加入 WebSocket，`*` 配置将允许预检请求通过任意方法/头。
- **建议**：收紧为 `["GET", "POST", "PUT", "DELETE"]` 和 `["Content-Type"]`。

### 1.4 🟡 错误响应泄露内部异常细节
- **位置**：`backend/api/routers/common.py` (L37)、`settings.py` 等多处 `HTTPException(status_code=500, detail=str(e))`
- **问题**：`str(e)` 可能包含文件路径、堆栈信息或系统细节，对客户端暴露过多。
- **建议**：500 错误仅返回通用消息，详细信息只写日志。

## 二、稳定性 / 健壮性问题

### 2.1 🔴 `LLMManager` 配置加载是一次性的，热更新模型配置不生效
- **位置**：`backend/utils/llm_manager.py::__init__` (L16-18)
- **问题**：`self.config = self._load_config()` 在实例化时从 `models.yaml` 读取一次。而 `ModelConfigService` 支持在线增删改模型，修改后 YAML 文件已变化，但 `BaseService` 持有的 `LLMManager` 实例仍使用旧配置。除非重启后端或创建新的 `BaseService` 实例，否则变更不会生效。
- **影响**：用户通过 Settings 页面修改模型配置后，实际生成仍使用旧模型，极易造成困惑。
- **建议**：`get_model_config()` 每次调用时重新读取 YAML，或引入文件 Watcher / 手动 reload 接口。

### 2.2 🔴 `BaseService` 在每个请求中重新实例化所有子服务
- **位置**：`backend/services/base.py::__init__` (L16-20)
- **问题**：每个 Stage Service 继承 `BaseService`，虽然 Service 本身可能是模块级单例或由 router 持有，但 `__init__` 中创建了 `LLMManager()`、`PromptManager()`、`FileManager()`、`ProjectService()` 四个新对象。若 router 层每次请求都 new 一个 Service，则每次都会读 YAML、初始化 Jinja2 环境等。
- **建议**：使用 FastAPI 的依赖注入（`Depends`）管理 Service 生命周期，或将 Manager 改为单例。

### 2.3 🟡 `DebugManager` 内存日志用全局变量，无线程安全保护
- **位置**：`backend/utils/debug_manager.py` (L7, L59-62)
- **问题**：`_MEMORY_LOGS` 是模块级全局列表，在 `log_interaction` 中通过 `insert(0, ...)` 和切片操作修改，无锁保护。FastAPI 使用 `uvicorn` 运行时若开启多线程/Worker，可能出现竞态条件。
- **建议**：使用 `collections.deque(maxlen=50)` 替代列表切片，或加 `threading.Lock`。

### 2.4 🟡 `DebugManager.LOG_DIR` 使用相对路径 `"logs"`
- **位置**：`backend/utils/debug_manager.py` (L15)
- **问题**：日志写入的目标由当前工作目录决定。若从非 `backend/` 目录启动，日志将写入意外位置。
- **建议**：改为基于 `__file__` 的绝对路径（如 `Path(__file__).parent.parent / "logs"`）。

### 2.5 🟡 OpenAI `httpx.Client` 未显式设置超时
- **位置**：`backend/utils/llm_gateway.py::_get_openai_client` (L24)
- **问题**：`httpx.Client()` 默认超时为 5 秒，对于大模型长文本生成可能不够。而 Google GenAI SDK 有自己的超时机制。
- **建议**：显式设置 `httpx.Client(timeout=httpx.Timeout(120.0))` 或更长时间。

### 2.6 🟡 重试机制过度捕获 `OSError`
- **位置**：`backend/utils/llm_gateway.py::_retry_wrapper` (L41)
- **问题**：`OSError` 是非常宽泛的基类（包含权限错误、磁盘满等），可能导致不应重试的错误被重试。
- **建议**：仅捕获 `ConnectionError`、`TimeoutError` 等网络相关子类。

### 2.7 🟡 JSON 解析失败时无恢复机制
- **位置**：`backend/utils/llm_manager.py` (L222)
- **问题**：`json.loads(cleaned_text)` 失败直接抛出异常。LLM 输出偶尔会包含尾部逗号、注释或不完整的 JSON。
- **建议**：增加 fallback 修复逻辑（移除尾部逗号、截断到最后一个 `}` 或 `]` 等），或重试一次 LLM 调用。

## 三、架构 / 设计问题

### 3.1 🟡 `FileManager.save_json` 与 `save_validated_json` 路径语义混乱
- **位置**：`backend/utils/file_manager.py::save_json` 接收绝对路径，`backend/services/base.py::save_validated_json` (L254) 注释写的是 relative_path
- **问题**：`save_validated_json` 的参数 `relative_path` 实际上被直接传给 `self.files.save_json(relative_path, data)`，而 `save_json` 把第一个参数当作绝对路径使用。调用方需要自行拼接绝对路径，但参数名/文档暗示是相对路径，容易引发误用。
- **建议**：统一路径语义：要么 `save_json` 接受项目相对路径并内部拼接，要么参数名/文档改为 `absolute_path`。

### 3.2 🟡 `RiskControl` 模块定义了但从未被使用
- **位置**：`backend/utils/risk_control.py`
- **问题**：`calculate_roi`、`check_finance_health`、`analyze_script_risks` 三个方法无任何调用者。模块仅有 `TODO` 占位逻辑。
- **建议**：若无近期使用计划，移至 `_archived` 或删除，避免增加维护负担。

### 3.3 🟡 `archive_service.py` 被 router 引用但未被审计中发现任何删除限制
- **位置**：`backend/api/routers/common.py` (L50-59)
- **问题**：`archive_project` 将项目复制到 `backup/` 目录，但 `delete_project` 并不检查是否已归档。用户可能意外先删除再归档，或归档后仍删除原始数据。
- **建议**：删除前可选的"已归档确认"提示，或在删除响应中提示用户先归档。

### 3.4 💡 前端 `api.ts` 缺少请求超时和取消机制
- **位置**：`frontend/lib/api.ts`
- **问题**：`fetchAPI` 使用原生 `fetch()` 无超时控制。LLM 生成可能耗时数分钟，期间用户无法取消，前端也无法区分超时与正常等待。
- **建议**：引入 `AbortController` 配合超时逻辑。

### 3.5 💡 `.gitignore` 注释与实际使用不符
- **位置**：`.gitignore` (L30-31)
- **问题**：注释写 `Frontend (Nuxt.js / Node)` 但实际使用 Next.js。`.nuxt/` 和 `.output/` 是 Nuxt 专用目录，不会出现在当前项目中。
- **建议**：更新注释为 Next.js，移除 `.nuxt/` 和 `.output/` 规则。

## 四、依赖 / 构建问题

### 4.1 🔴 `requirements.txt` 无版本锁定
- **位置**：`backend/requirements.txt`
- **问题**：所有 13 个依赖均未指定版本号（如 `fastapi`、`google-genai`、`openai`）。`google-genai` 和 `openai` 的 SDK API 在大版本间有破坏性变更history。
- **建议**：至少指定最低版本或精确版本（如 `fastapi>=0.115`、`google-genai>=1.0,<2.0`）。更好的做法是添加 `requirements-lock.txt`。

### 4.2 🟡 `tenacity` 和 `requests` 被安装但从未使用
- **位置**：`backend/requirements.txt` (L8-9)
- **问题**：代码中重试逻辑使用自定义 `_retry_wrapper`（不依赖 `tenacity`），HTTP 请求使用 `httpx`（不依赖 `requests`）。这两个包是不必要的依赖。
- **建议**：移除 `tenacity` 和 `requests`，或用 `tenacity` 替换自定义重试逻辑。

### 4.3 🟡 `watchdog` 被安装但无使用痕迹
- **位置**：`backend/requirements.txt` (L10)
- **问题**：`watchdog` 通常用于文件监听，但代码中未 import 过。可能是历史残留。
- **建议**：移除。

### 4.4 💡 `install.sh` 硬编码清华镜像和 npm 镜像
- **位置**：`install.sh` (L43, L64)
- **问题**：`pip install -i https://pypi.tuna.tsinghua.edu.cn/simple` 和 `npm install --registry=https://registry.npmmirror.com` 对中国国内用户友好，但国际用户访问这些镜像可能反而更慢或不可用。
- **建议**：加入 `--mirror` 参数或检测网络环境后自动选择镜像。

### 4.5 💡 `start.sh` 使用 `npm run start`（生产模式）但未检查 build 产物
- **位置**：`start.sh` (L37)
- **问题**：`npm run start` 运行 `next start`，需要先 `next build` 产出 `.next/` 目录。若用户修改了前端代码但未重新 build，将运行旧版本。
- **建议**：启动前检查 `.next/` 是否存在且不早于源码修改时间，或提供 `start-dev.sh` 使用 `npm run dev`。

## 五、代码质量 / 维护性问题

### 5.1 🟡 大量 bare `except` / `except:` 吞没异常
- **位置**（举例）：
  - `cache_manager.py` L77: `except: return None`
  - `cache_manager.py` L93: `except: return False`
  - `debug_manager.py` L94: `except: pass`
  - `cache_manager.py` L147: `except: expire_str = str(...)`
  - `model_config_service.py` L79: `except: return False`
- **问题**：bare `except` 会吞掉 `KeyboardInterrupt`、`SystemExit` 等不应被捕获的异常，且无日志输出导致调试困难。
- **建议**：统一改为 `except Exception as e` 并记录日志。

### 5.2 🟡 `print()` 作为唯一日志手段
- **位置**：全项目通用（`base.py`、`llm_manager.py`、`cache_manager.py`、`project_service.py` 等数十处）
- **问题**：`print()` 不带时间戳、级别、来源等结构化信息。虽然 `logging_config.py` 配置了 `setup_chinese_logging()`，但实际代码中几乎未使用 `logging` 模块。
- **建议**：将 `print()` 替换为 `logging.getLogger(__name__).info/warning/error(...)`。

### 5.3 🟡 `import json` 在函数内部重复引用
- **位置**：`project_service.py` L119, L141, L182
- **问题**：`json` 在三个方法中分别 `import json`，而非文件头部统一引入。
- **建议**：移至文件顶部。

### 5.4 💡 `api_key_service.py::validate_key` 使用硬编码的 provider 推断
- **位置**：`backend/services/api_key_service.py` (L152-168)
- **问题**：通过 `"GEMINI" in key_name.upper()` 推断 provider 类型。若用户自定义 Key 名不含 "GEMINI" 或 "DEEPSEEK"，验证会跳过。DeepSeek `base_url` 也是硬编码的。
- **建议**：从 `models.yaml` 中读取 Key 对应的 provider 和 base_url 来进行验证。

### 5.5 💡 `_write_env` 值包含引号时的双重引号问题
- **位置**：`backend/services/api_key_service.py::_write_env` (L43-46)
- **问题**：当值中含 `"` 时，用 `f'"{value}"'` 包裹会导致内部引号未转义。例如 `value = 'abc"def'` → 写入 `KEY="abc"def"`，再读取时解析错误。
- **建议**：对值进行转义处理或使用 `python-dotenv` 的 `set_key` 函数。
